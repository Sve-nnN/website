### Non-blocking gap 2 — Pre-existing bug found during audit (not caused by v1.2)

`GET /api/posts` (public REST API) returns `HTTP 500` whenever `depth >= 1` is requested (the default the REST API otherwise uses for relation population), for unauthenticated requests. Root cause: `Categories` collection uses `access.read = authenticatedOrPublished`, which filters by `_status: { equals: 'published' }`, but `Categories` has no `versions.drafts` config — so it has no `_status` column at all, and the query throws `APIError: Cannot find field for path at _status` when Posts' `categories` relation is populated for an anonymous request.

- **Traced to Phase 1** (`f4cef7e feat(01-02): add Users, Media, Categories collections`), not introduced by v1.2 — confirmed via `git log --follow` on both `Categories/index.ts` and `authenticatedOrPublished.ts`.
- **Does not affect the actual site** — all frontend pages (blog listing, blog detail, etc.) use Payload's Local API (`overrideAccess: true` by default), which bypasses the access-control `where` injection entirely; this is why every frontend page spot-checked above returned 200 with correct content despite this bug.
- **Does affect** any external consumer hitting `/api/posts` directly with depth ≥ 1 while unauthenticated (e.g., a future integration, a headless client, or manual API exploration) — those get a 500 instead of data.
- **Fix (for a future phase, not v1.2):** either give `Categories` proper `versions: { drafts: true }` support (if drafts make sense for taxonomy) or change `Categories.access.read` to a simple `() => true` (matching `Authors.access.read`, since categories are non-sensitive public taxonomy with no draft workflow needed).

This is flagged for Juan's awareness and a future quick-fix phase; it does not block v1.2 closure since it's unrelated to any of the 18 v1.2 requirements and pre-dates this milestone by many phases.
