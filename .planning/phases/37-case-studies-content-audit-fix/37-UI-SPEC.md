## Fix 2 — Results Chart: Dual-Axis Scale + Mobile (CASE-09, CASE-10)

**Locked decision (37-CONTEXT.md):** group `results.metrics` rows by order of magnitude and render two Y-axes (`yAxisId="left"` / `yAxisId="right"`) inside the same `BarChart` — do NOT normalize to percentages (loses the real magnitude Juan wants to show) and do NOT split into separate chart components.

### Magnitude grouping algorithm (executor discretion per CONTEXT.md, contract below is the guardrail)

1. For each row produced by `buildChartRows()`, compute `magnitude = Math.max(Math.abs(row.before), Math.abs(row.after))`.
2. Bucket rows into exactly 2 groups by order of magnitude (`Math.floor(Math.log10(magnitude))`), split at the largest gap between consecutive orders — e.g. position (~8, order 0) and CTR% (~3, order 0) land in one bucket; impressions (~30,000, order 4) and clicks (~2,000, order 3) land in the other. If all rows land in the same order of magnitude, render a single shared axis (no dual-axis needed) rather than forcing an artificial split.
3. Assign the low-magnitude bucket to `yAxisId="left"`, high-magnitude bucket to `yAxisId="right"`. Every `<Bar>` for a given metric name must reference the same `yAxisId` for both its `before` and `after` series.

### Axis + series contract

| Element | Value |
|---------|-------|
| Left Y-axis | `yAxisId="left"`, `orientation="left"`, low-magnitude bucket, `tick={{ fontSize: 11 }}`, `width={40}` (existing values) |
| Right Y-axis | `yAxisId="right"`, `orientation="right"`, high-magnitude bucket, same tick/width styling as left for visual parity |
| Bar colors | Unchanged — `before` = `var(--color-before)` (maps to `--chart-2`), `after` = `var(--color-after)` (maps to `--chart-1`). Dual-axis is a scale fix, not a new color scheme — do not introduce `--chart-3`+ for this. |
| Legend / labels | `ChartTooltipContent` unchanged; each metric's `label` (already required+localized in schema) is the sole X-axis tick text — no new copy needed |
| X-axis | `interval={0}` (all labels always shown, no skipping) — unchanged from current implementation |

### Mobile contract (< 400px viewport, CASE-10)

| Concern | Requirement |
|---------|-------------|
| Overflow | `ChartContainer` stays `w-full` inside `Container` (existing) — the chart must never force horizontal scroll on the page at 375px |
| X-axis label legibility | If dual-axis label width is a problem at 375px with more than ~4 metric rows, reduce `tick.fontSize` to 10px (min floor — do not go below 10px) and/or angle labels (`angle={-30}`, `textAnchor="end"`) rather than truncating label text; the metric `label` field is real content and must remain fully legible, not clipped |
| Bar width / crowding | If more metrics are added per CASE-04/06 (more rows than today's 1-2), verify bars don't compress below a tappable/readable width at 375px — if crowding occurs, prefer wrapping to `barCategoryGap`/`barGap` adjustments over shrinking font below the 10px floor |
| Verification | Must be checked live against the running dev server at 375px (real browser or headless), not inferred from code — per the project's established mobile-first verification discipline (Phase 10.6/11 precedent) |

No new spacing scale, no new typography — `text-label`/`text-muted-foreground` around the chart (periodBefore/periodAfter caption, metric cards below) are unchanged existing tokens.

## Fix 3 — Structural Benchmark vs ariannalupi.com/casos (CASE-11)

**Reference structure observed** (`ariannalupi.com/casos/ecommerce-vape/`, structure only, no content copied):
1. Nav header
2. Hero (title + metric headline + subtitle)
3. Client overview (brief intro)
4. KPI cards (4)
5. Challenge (numbered list)
6. Solution (numbered steps)
7. Results (before/after by metric)
8. Conclusion / insight
9. **Closing CTA** (question prompt + 2 buttons: contact + view more case studies)
10. Footer

**Current page structure** (`case-studies/[slug]/page.tsx`): Hero → KPIs → Client (`clientContext`) → Challenge → Solution → optional Testimonial → Results (chart + metric cards) → Conclusion → Author.

**Gap identified:** the reference page ends with a closing CTA section driving the visitor to a next action (contact / more case studies) before the footer. The current page ends on Author, with no explicit next-step CTA. This is the one genuinely-missing piece that fits the existing data model without a schema change or layout rebuild — everything else (client overview, KPIs, challenge, solution, results, conclusion) already exists.

### New section contract: Closing CTA

| Property | Value |
|----------|-------|
| Placement | After the `conclusion` section, before the `author` section (matches reference order: insight → CTA → footer/author-adjacent content) |
| Data source | **No new Payload field.** Static, locale-aware copy block (same pattern as hardcoded `copy` object already at the top of `page.tsx` for `client`/`challenge`/`solution`/`results`/`before`/`after` labels) — this is chrome copy, not per-case-study editorial content, consistent with how the rest of this page's section labels are already handled |
| Layout | `<section>` inside the existing `Container`, `text-center`, vertical rhythm `mt-10` matching sibling sections (`t.challenge`/`t.solution`/`t.results` all use `mt-10 mb-4` on their `<h2>`) |
| Heading | `font-heading text-heading` (existing token, matches all other section headings on this page) |
| Buttons | 2 CTAs using existing `Button` primitive (shadcn, already styled by Phase 8): 1 primary (`variant="default"`) linking to `/contact` (locale-aware), 1 secondary (`variant="outline"` or `variant="secondary"`) linking to `/case-studies` (locale-aware, listing page) |
| Spacing between buttons | `gap-4` (existing `md` token), `flex flex-wrap justify-center` for mobile stacking at 375px |

### Copywriting for the new CTA (both locales, to be added to the page's existing `copy` object)

| Element | ES | EN |
|---------|-----|-----|
| CTA heading | "¿Quieres resultados como estos?" | "Want results like these?" |
| Primary button | "Hablemos de tu proyecto" | "Let's talk about your project" |
| Secondary button | "Ver más casos de éxito" | "See more case studies" |

No other structural additions — per CONTEXT.md, do not redesign the layout or add sections that don't fit the KPI/challenge/solution/results model (e.g. no pricing table, no author bio duplicated a second time, no new hero variant).
