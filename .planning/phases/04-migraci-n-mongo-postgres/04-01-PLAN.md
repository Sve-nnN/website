<resolution_technique>
## Por qué el dump vive en un script único (Wave 1) y no se repite

Importar el `payload.config.ts` real de JuanPortfolio desde un script que corre en el proyecto `juan-payload` es fráفil: varios archivos de colección de JuanPortfolio (`Posts/index.ts`, `Categories.ts`, `Authors/index.ts`) usan imports reales con el alias `@/*` (p.ej. `@/fields/slug`, `@/utilities/adminGroups`, `@/utilities/seo/seoFields`, `@/access/authenticated`) que solo resuelven contra EL tsconfig.json de JuanPortfolio, no el de juan-payload.

Solución: ejecutar el script de dump con la variable de entorno `TSX_TSCONFIG_PATH` apuntando explícitamente al tsconfig de JuanPortfolio, mientras el import del config sigue siendo un import relativo normal (Node resuelve imports relativos por la ubicación del archivo, no por el cwd, así que esto siempre funciona sin importar el truco del tsconfig):

```
TSX_TSCONFIG_PATH=/Users/juan/Documents/Codigo/Personal/juantech/JuanPortfolio/tsconfig.json npx tsx scripts/migrate/export/dump-source.ts
```

Si la versión instalada de `tsx` no respeta `TSX_TSCONFIG_PATH` (verificar con `npx tsx --version`; la variable requiere tsx >= 4.15), el fallback es ejecutar el mismo script cambiando el cwd al de JuanPortfolio (el import relativo del config sigue funcionando igual, y con cwd=JuanPortfolio el tsconfig correcto se detecta por herencia de árbol):

```
(cd /Users/juan/Documents/Codigo/Personal/juantech/JuanPortfolio && npx tsx /Users/juan/Documents/Codigo/Personal/juantech/juan-payload/scripts/migrate/export/dump-source.ts)
```

Este es el ÚNICO punto de toda la fase 4 donde se toca el config/Mongo real de JuanPortfolio. Todo lo demás (waves 2-8) lee exclusivamente los JSON ya volcados en `scripts/migrate/data/export/`.
</resolution_technique>
