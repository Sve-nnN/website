<objective>
Construir el segundo consumidor de `AffiliateLink`/`AffiliateDisclosure`: un bloque inline de Lexical
(`affiliate-inline`) que un editor puede insertar dentro del cuerpo de cualquier post, y el escaneo
puro que decide si el post necesita mostrar el disclosure legal antes de su cuerpo. A diferencia de
`ToolStack` (Plan 48-01/48-02), esto NO toca schema de Postgres — `posts.content` ya es `jsonb`.

Purpose: INL-01/INL-02 son la segunda superficie de afiliados del ROADMAP — sin esto, cualquier
mención de una herramienta dentro de un artículo del blog no puede llevar un CTA de afiliado
correctamente formado ni un disclosure.
Output: bloque Lexical registrado, componente leaf sin el hazard de TDZ, disclosure auto-inyectado en
la página de detalle de post, y al menos un post real demostrando ambos de punta a punta.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Editor autenticado -> contenido Lexical de un Post | El admin inserta un bloque `affiliate-inline` dentro del rich text; el frontend confía en la forma del nodo al leerlo de vuelta |
| Visitante anónimo -> post con bloque inline | Lectura pública, sin input del visitante |
| Build de Next.js -> grafo de imports de `richTextBlockConverters.tsx` | Un import mal puesto rompe el build entero (TDZ), no solo esta feature — superficie de disponibilidad, no de confidencialidad |
