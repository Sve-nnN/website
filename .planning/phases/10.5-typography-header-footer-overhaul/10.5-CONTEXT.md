## Implementation Decisions

### Why this phase exists (context for the executor)
Juan reviewed the live site after Phase 10 closed and gave direct negative feedback: "las fuentes no me gustan, el footer no me gusta, no tiene nada, el header tampoco me gusta, esta muy simple... debe ser mobile first." This is a genuine reopening of visual decisions locked in `05-UI-SPEC.md` (typography) and extends Phase 8's SiteHeader/SiteFooter work (which only did token-consistency styling, not a structural/content richness pass). This phase supersedes the relevant parts of `05-UI-SPEC.md` and Phase 8's header/footer scope — do not treat those as immutable priors for the specific items below.

### Typography — use auditor's font stack
- Adopt the exact same 4-font stack as `/Users/juan/Documents/Codigo/Personal/juantech/auditor/apps/web`:
  - **Array** (display/headline font) — local self-hosted woff2, single weight 400. File exists at `/Users/juan/Documents/Codigo/Personal/juantech/auditor/apps/web/app/fonts/Array-Regular.woff2` (21KB) — copy this file into this project (e.g. `src/fonts/Array-Regular.woff2` or wherever this project's font convention lives). Verify its license permits this reuse (Array is commonly distributed under SIL OFL — confirm before shipping, don't assume).
  - **Khand** (headings/UI) — Google Font, self-hosted via `next/font/google`, weights 400/500/600/700.
  - **Geist Sans** (body) — via the `geist` npm package (`geist/font/sans`).
  - **Geist Mono** (code/mono contexts) — via the `geist` npm package (`geist/font/mono`), for any inline code/mono usage this site has (e.g. within Prose code blocks).
- Replace Inter+Fraunces entirely — remove the `next/font/google` Inter/Fraunces setup, replace all `font-display`/`font-sans` (or equivalent) token usage across the codebase to point at the new families.
- Follow `auditor`'s own module pattern for defining fonts (see `app/fonts.ts` there) — a single fonts module exporting the four font objects with `.variable` CSS variables, wired once in the root layout, `display: swap`, sensible system-font fallbacks.
- This is a genuine reopening of `05-UI-SPEC.md`'s locked Inter+Fraunces decision — document this override explicitly (in this phase's SUMMARY and by updating the relevant section of `05-UI-SPEC.md` or noting the supersession) rather than leaving two contradictory "locked" specs in the repo.

### Header — full navigation, not "simple"
- Expand `SiteHeader` to show real, visible navigation links (Blog, Case Studies, Authors, Contact — or whatever set makes sense) at desktop width, not just a logo + CTA button + locale switcher.
- The `Header` global's `navItems` array field already exists in Payload (`src/globals/Header/index.ts`) — this phase is primarily a RENDERING/visual gap (the field exists, the component isn't giving it visual prominence), verify whether `navItems` is even being read/rendered by `SiteHeader.tsx` today and fix if it's missing entirely from the render, then style it properly.
- Mobile-first: design and verify the mobile nav (likely the existing `Sheet`/hamburger menu component, already imported in `SiteHeader.tsx`) FIRST, then progressively enhance for tablet/desktop — not the other way around.

### Footer — rich, editable, with dynamic content sections
- Footer must feel substantial, not empty. Juan explicitly wants:
  - Editable columns (already exists: `Footer.columns[]` with manual link groups) — keep this.
  - NEW: at least one column/section capable of showing **dynamic content** — specifically "los últimos 5 blog posts" and "los últimos 5 casos de estudio" — computed at render time from real Payload data (most recent by date), not manually curated links. This needs a genuine schema addition to the `Footer` global (e.g. a `type` field per column: `manual` vs `latestPosts` vs `latestCaseStudies`, or a separate toggle/section outside the manual `columns[]` array) — this IS new Payload schema work, which is explicitly IN SCOPE for this phase (unlike Phases 7-10's "zero config.ts diff" constraint, which does not apply here since this is new functionality Juan is requesting, not a violation of the visual-only constraint).
  - Navigational links (already exists: `columns[]`, `legalLinks[]`) — keep, but treat as one section among several, not the only content.
  - Keep the existing `socialLinks[]` section.
- The footer's visual density should read as "a real site footer" (multi-column, real content, not sparse) — informed by the level of detail `.planning/research/FEATURES.md` documented for professional portfolio sites, but the specific ask (dynamic latest-content columns) is Juan's explicit direction, not something to re-derive from research.
- Mobile-first: design the stacked mobile footer layout first (likely single-column, collapsible or straightforward vertical stack), then expand to the multi-column desktop grid.

### Mobile-first — applies going forward
- From this phase onward (including the eventual Phase 11 re-run), all visual work in this milestone is verified mobile-first: build/check at ~375px first, then progressively verify tablet (~768px) and desktop (~1280px) — not desktop-first with a mobile "check" at the end, which was the pattern used (and insufficiently verified, per Phase 10/11's own admitted tooling gaps) through Phase 10.
- This phase and any remaining work should explicitly test real mobile viewport widths, not just note "no viewport-resize tool available" and skip it — find a way (browser dev tools via any available browser automation, or at minimum careful CSS review for mobile-first utility ordering) to actually verify mobile rendering, not just claim low residual risk.

### Scope discipline (carried from the rest of the milestone)
- No new page-builder/motion-JS libraries beyond what's needed for the font packages themselves (`geist` npm package, Google Fonts via `next/font/google` for Khand — both are the SAME mechanism already used for Inter/Fraunces, not a new category of dependency).
- Copy stays Payload-sourced. The new footer dynamic-content columns pull from real Posts/CaseStudies collections via the Local API at render time — not hardcoded.
- This phase's Payload schema change (Footer global's new dynamic-column capability) needs a migration (`payload migrate:create`) per this project's established schema discipline (`push:false` always) — this is a legitimate, planned schema change, not an accidental one.
