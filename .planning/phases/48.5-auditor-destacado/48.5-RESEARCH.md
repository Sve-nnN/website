## Summary

Esta fase es puramente aditiva sobre un patrón que ya existe tres veces en el repo (`ServicesShowcase`, `AuditOfferBlock`, `StackHighlightCallout`) y no toca ninguna de las piezas de infraestructura de afiliados (Phase 46-48) — es la primera fase del milestone v2.1 que **no** depende de `affiliate-links`/`/go/`/disclosure. El trabajo real son 3 superficies nuevas: un bloque `AuditorHighlight` en Home (nuevo, config+component), un bloque `AuditorCallout` en la landing de Auditoría SEO Técnica (nuevo, config+component wrapping `StackHighlightCallout`), y una tercera instancia de `StackHighlightCallout` en `/stack` vía un campo `group` nuevo en `ToolStack.config.ts`.

Confirmé en vivo (curl contra producción, 2026-09-06) que el orden de bloques de Home que describe el UI-SPEC es exacto: `Hero → ClientLogosBlock ("Con quiénes trabajé") → CodeFixesBlock ("Errores reales...") → ServicesShowcase ("Cómo puedo ayudarte") → AboutSection ("Mi enfoque en Consultoría Técnica") → AuditOfferBlock ("Empecemos por una auditoría técnica") → ContactFormBlock ("Hablemos")`. El nuevo `AuditorHighlight` encaja exactamente donde dice el UI-SPEC — entre `ServicesShowcase` y `AboutSection` — con `AboutSection` funcionando de colchón real (no hipotético) antes de llegar al bloque del audit pagado de 600 USD. También confirmé el orden de la landing `/servicios/seo-technical-audit` (`Hero → intro → ServiceScopeCard → ClientLogosBlock → Testimonios → RelatedCaseStudyBlock → FAQ`) y que `ServiceScopeCard` aparece con el mismo patrón ("Alcance de X") en las otras 3 landings de servicio (`seo-consulting`, `fullstack-development`, `ai-seo-geo`) — confirmando que es compartido y no debe tocarse.

Hallazgo no anticipado, importante para el plan: la rama actual (`docs/seo-handoff`) está **65 commits adelante de `master` y 0 detrás**, y `src/app/(frontend)/[locale]/stack/page.tsx` **no existe en `master`**. Producción (`juan-tech.com`, que despliega automáticamente al mergear a `master` vía Dokploy, per memoria del proyecto) todavía no tiene la Phase 48 — por eso `curl https://juan-tech.com/stack` devuelve 404 en este momento. Esto es esperado, no un bug: `ServicesShowcase` y `AuditOfferBlock` sí están en `master` (verificado con `git show master:<path>`), así que el curl de Home funcionó correctamente, pero la verificación en vivo de la tercera instancia de `StackHighlightCallout` en `/stack` (parte de FEAT-03) no podrá hacerse contra producción hasta que la Phase 48 llegue a `master`. El plan debe verificar `/stack` contra el dev server local o contra el HEAD de la rama actual, no contra `juan-tech.com`.

Segundo hallazgo: el prop actual de `StackHighlightCallout` es `gscHref`/`gscLabel` (nombrado por su único caller anterior, Google Search Console). El UI-SPEC pide generalizar a `linkHref`/`linkLabel` como parte de esta fase — eso implica editar tanto el componente como su único call site actual en `ToolStackComponent.tsx` (líneas 92-97), no solo agregar una tercera instancia.

**Primary recommendation:** construir `AuditorHighlight` y `AuditorCallout` como blocks nuevos siguiendo exactamente la forma minimalista de `config.ts` de `ServicesShowcase` (pocos campos editoriales, datos verificables hardcodeados en un módulo `src/lib/auditor.ts` nuevo), generalizar `StackHighlightCallout`'s props de `gscHref/gscLabel` a `linkHref/linkLabel` actualizando su único call site existente, y usar el ancla `<a rel="noopener" target="_blank">` ya presente en `StackHighlightCallout.tsx:38-42` como plantilla exacta para las 3 superficies — nunca el `rel="sponsored nofollow noopener"` de `AffiliateLink.tsx` ni el `rel="noopener noreferrer"` de `AuthorCard.tsx`.

### Pattern 1: `ServicesShowcase` — el patrón de bloque que FEAT-01 exige seguir
**Qué es:** un `Block` de Payload con **un solo campo editorial** (`title`, text, localized, no required) más un `Component.tsx` que resuelve el resto del contenido desde una fuente de datos fija en código, no desde campos del CMS.

**Config.ts leído completo** `[VERIFIED: src/blocks/ServicesShowcase/config.ts:1-23]`:
```typescript
export const ServicesShowcase: Block = {
  slug: 'servicesShowcase',
  interfaceName: 'ServicesShowcaseBlock',
  labels: { singular: 'Services Showcase', plural: 'Services Showcase Blocks' },
  fields: [
    {
      name: 'title',
      type: 'text',
      localized: true,
      admin: {
        description: 'Section heading — editable per page instance.',
      },
    },
  ],
}
```

**Component.tsx leído completo** `[VERIFIED: src/blocks/ServicesShowcase/Component.tsx:1-97]` — puntos clave a replicar en `AuditorHighlight`:
- `sr-only` fallback heading cuando `title` está vacío (comentario `SEO-10.2`: nunca saltar un nivel de heading) — el UI-SPEC pide exactamente este patrón para `AuditorHighlight.title`.
- Ícono via mapa hardcodeado (`iconBySlug`), no campo CMS — mismo principio para `Gauge` en `AuditorHighlight` (no hay campo `icon`).
- `Container className="py-12"` para el grid de 4 tarjetas — pero el UI-SPEC pide `py-16` para `AuditorHighlight` porque es "feature-weight", no un grid de 4 — **no copiar el spacing de `ServicesShowcase` literal, solo la forma del block**.
- `<Link>` envuelve toda la card porque es navegación interna — el UI-SPEC exige explícitamente **no** replicar esto para `AuditorHighlight`: el CTA debe ser un `<Button>`/`<a>` explícito, no toda la card clicable, porque cruza a otro dominio.

### Anti-Patterns to Avoid
- **Whole-card `<Link>` para el CTA de `AuditorHighlight`:** correcto para `ServicesShowcase` (navegación interna), incorrecto acá — cruza a otro dominio, debe ser un `Button`/`<a>` explícito (ya resuelto por UI-SPEC, documentado acá para que el ejecutor no "simplifique" copiando el patrón de `ServicesShowcase` al pie de la letra).
- **Reusar `rel="sponsored nofollow noopener"` de `AffiliateLink.tsx`:** es literalmente incorrecto para este caso — declararía una relación de afiliado que no existe (constraint dura FEAT-04/CONTEXT.md).
- **Reusar `rel="noopener noreferrer"` de `AuthorCard.tsx`:** es un patrón válido en otro contexto (social links), pero no es el que pide el UI-SPEC para estos 3 links — el UI-SPEC especifica `rel="noopener"` únicamente, mirroring el link de GSC existente. Usar `noreferrer` de más no rompe nada funcionalmente, pero diverge del contrato checker-approved.
- **Agregar un campo al `ServiceScopeCard` compartido en vez de un block nuevo:** contaminaría el admin de las otras 3 landings de servicio con un campo irrelevante — el UI-SPEC ya descarta esto explícitamente y la verificación en vivo confirma que `ServiceScopeCard` es realmente compartido.
- **Verificar `/stack` contra `https://juan-tech.com/stack`:** la Phase 48 (que crea `/stack`) todavía no está en `master`/producción — esa URL da 404 hoy. Verificar contra el dev server local o el build de la rama actual.

## Common Pitfalls

### Pitfall 1: Confundir "sin migración" con "sin cambio de schema"
**What goes wrong:** asumir que como `ToolStack` ya existe, agregar el campo `auditorHighlight` no necesita migración.
**Why it happens:** el precedente de Phase 48 (INL-01) sí fue "sin migración" porque el inline block vive en una columna `jsonb` existente — es fácil generalizar mal esa lección.
**How to avoid:** cualquier campo nuevo en un `Block`/`CollectionConfig` de Payload sobre el adapter Postgres genera DDL (`ADD COLUMN` en el caso de un `group` field escalar como este, `CREATE TABLE` en el caso de los 2 blocks nuevos). Correr `payload migrate:create`, leer el SQL generado, confirmar que es 100% aditivo (`ADD COLUMN`/`CREATE TABLE`, sin `DROP`), y solo entonces `payload migrate` — sin pedir confirmación a Juan (regla dura de CLAUDE.md para migraciones aditivas).
**Warning signs:** el SQL generado contiene `DROP COLUMN`, `ALTER COLUMN ... TYPE`, o toca `pages_blocks_tool_stack_locales` de forma distinta a un `ADD COLUMN` simple.

### Pitfall 2: Editar `StackHighlightCallout` sin actualizar su único call site
**What goes wrong:** renombrar `gscHref`/`gscLabel` a `linkHref`/`linkLabel` en la firma del componente sin tocar `ToolStackComponent.tsx:92-97`, rompiendo el build (TypeScript) o silenciosamente dejando de pasar el link de GSC.
**Why it happens:** el cambio de props está en un archivo distinto del que se está "agregando" (la 3ra instancia).
**How to avoid:** el plan debe incluir explícitamente la edición de `ToolStackComponent.tsx` como parte de la misma tarea que renombra los props, verificando `tsc --noEmit` o build local antes de dar la tarea por cerrada.

### Pitfall 3: Verificar contra producción una ruta que todavía no está desplegada
**What goes wrong:** intentar confirmar el resultado final con `curl https://juan-tech.com/stack` y interpretar el 404 como que algo salió mal en esta fase.
**Why it happens:** el resto del milestone (Home, la landing de servicios) sí está en producción, generando la expectativa de que todo lo demás también lo esté.
**How to avoid:** confirmado con `git rev-list --left-right --count master...HEAD` (0 detrás, 65 adelante) y `git show master:"src/app/.../stack/page.tsx"` (vacío) que `/stack` no existe en `master` todavía. Verificar `/stack` contra el dev server local (`payload run` + `next dev`, o el build de la rama actual) hasta que Phase 48 llegue a producción.

### Pitfall 4: Publicar los docs actualizados en estado `draft`
**What goes wrong:** el bug recurrente ya documentado en memoria del proyecto — escrituras vía Local API/scripts que dejan `_status: 'draft'` por omisión, auto-verificándose como "escrito" mientras producción sigue sirviendo el contenido viejo.
**Why it happens:** el default de Payload para `versions.drafts` es no forzar `published` a menos que se pase explícitamente.
**How to avoid:** cualquier escritura a `home`, `seo-technical-audit`, o `stack` vía Local API/admin debe pasar `draft: false` (`_status: 'published'`) explícitamente. Ya está documentado en UI-SPEC como "known incident, not new to this phase".
