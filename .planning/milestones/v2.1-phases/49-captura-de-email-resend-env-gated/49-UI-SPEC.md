# Phase 49 — UI Design Contract

> Visual and interaction contract for the inline email-capture block (`posts.content`), its
> Server-Action submit states, the double opt-in confirmation page, and the lead magnet PDF's own
> print layout. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Governing rule (49-CONTEXT.md hard constraints):** never a popup/modal, zero client JavaScript,
> inline-in-posts only (no footer, no `/stack`, no dedicated landing page), env-gated clean
> degradation without `RESEND_API_KEY`. Every token below reuses the project's already-implemented
> design system (`src/app/globals.css`, `tailwind.config.ts`) and the exact structural pattern of
> `AffiliateInlineBlock`/`AffiliateInlineCard` (Phase 48) and `ContactFormBlockComponent` (Phase 5) —
> nothing here introduces a new visual language.

## Component Contract Detail (traceability for planner/executor)

### `EmailCaptureBlock` (`src/blocks/EmailCaptureBlock/{config.ts,Component.tsx}`)
- Registered as a second entry in the same `BlocksFeature({ blocks: [...] })` array Phase 48 added
  to `posts.content`'s `lexicalEditor()` config (`src/collections/Posts/index.ts`) — no new
  `BlocksFeature` call, just one more block slug alongside `affiliate-inline`.
- Admin-facing fields (shape, not schema — exact field names are the planner's call): the lead
  magnet is a fixed, singular concept for this phase (one checklist, two locale-specific PDFs), so
  the block itself needs **no relationship field** analogous to `AffiliateInlineBlock.affiliateLink`
  — it can be a zero-config block (editor just drops it into the article body) or carry a single
  optional `variant`/`heading` override if the planner decides per-post copy customization is
  useful. Default to zero-config unless research surfaces a reason otherwise; the copy in this
  spec's Copywriting Contract is designed to work unmodified on any post.
- **Single field, not name+email:** the form asks for email only. Rationale: this is a lead-magnet
  opt-in, not a contact form — every field beyond email adds friction with no benefit to a PDF
  delivery flow, and the double opt-in confirmation click is already the trust-building step.
- **Frontend converter:** added to `richTextConverters.blocks` in `richTextBlockConverters.tsx`,
  keyed `'email-capture'`, alongside the existing `'code-block'`/`'faq'`/`'affiliate-inline'`
  entries. **Same TDZ/circular-import isolation applies:** this component must NOT import
  `RichTextRenderer`, `AffiliateDisclosure`, or `FAQComponent` (or anything that transitively
  imports them) — only the Server Action, shadcn `Input`/`Button`, and a plain `<a>` for the
  privacy link.
- **Visual anatomy (vertical stack, `not-prose`, distinguishing it from the horizontal
  `AffiliateInlineCard` row):**
```
div.not-prose.my-8.rounded-lg.border.border-border.bg-card.shadow-sm.p-6
  p.text-label.uppercase.tracking-wide.opacity-70   — eyebrow ("Free download" / "Descarga gratis")
  p.font-heading.text-heading.mt-1                  — heading
  p.text-body.text-muted-foreground.mt-2            — description

  [state: form, default]
  form.mt-4
    label.sr-only (htmlFor="email-capture-{instance}") — "Email address" / "Correo electrónico"
    div.flex.flex-col.sm:flex-row.gap-2
      Input#email-capture-{instance}[type=email, name=email, required, autoComplete=email,
        placeholder, className="h-11 flex-1"]
      Button[type=submit, className="h-11 shrink-0"] — CTA label
    input[type=hidden, name=postSlug/locale]          — needed by the Server Action to build the
                                                          confirmation-email link and the redirect
    div[honeypot, hidden via CSS like ContactFormBlockComponent's company_website field]
    p.text-label.text-muted-foreground.mt-3            — privacy microcopy w/ inline link to /privacy

  [state: pending | already | error, after Server Action redirect]
  — the form above is replaced (not merely disabled) by:
  div.mt-4
    p.font-heading.text-heading  — state heading (Copywriting Contract)
    p.text-body(.text-destructive if error)  — state body
```
- **Reading confirmation state:** a single, page-wide query param (e.g. `?subscribed=pending|
  already|error`), NOT a per-block-instance identifier. Rationale (dismissed edge case): a post
  realistically carries at most one `EmailCaptureBlock` instance (editorial choice, same as
  `affiliate-inline` in practice); if a post ever had more than one, every instance would show the
  same confirmation state simultaneously, which is an acceptable, low-likelihood simplification
  rather than engineering per-instance anchor IDs for a case that doesn't occur in current content.
- **Real architecture wrinkle for the planner (the one place this block breaks from
  `AffiliateInlineCard`'s "no external context" shape):** `richTextConverters` is exported today as
  a static, module-level object built by `JSXConvertersFunction` with no per-request arguments. To
  let `EmailCaptureBlock` read the post page's `searchParams.subscribed`, the post-detail page needs
  to construct its converters per-request (e.g., a small factory wrapping the existing
  `richTextConverters` and closing over `subscribedState`, passed to `<RichText converters={...} />`
  instead of the static const). This is a genuinely new wiring shape versus `FaqBlockNode`/
  `AffiliateInlineCard`/`CodeBlockNode`, which take no request-scoped input — call this out
  explicitly in planning, do not assume it falls out "for free" from the existing pattern.
- **Server Action feasibility (already proven in this repo):** `ContactFormBlockComponent` already
  ships a zero-client-JS `<form action={onSubmit}>` with `onSubmit` a `'use server'` action passed
  as a prop into a Server Component, no `'use client'` directive anywhere in that file. This is the
  exact shape to replicate — no `onChange`, no client-side validation library, native `required`/
  `type="email"` only. The one untested wrinkle: no prior form (only plain anchors, e.g.
  `AffiliateLink`) has been mounted this deep inside a Lexical rich-text converter tree before —
  smoke-test the Server Action reference resolves correctly from that nesting depth before
  considering this block done.
- **Rate limiting:** reuse the exact in-memory per-IP pattern already in
  `src/app/actions/contact.ts` (`submissionLog` Map, module-level state — valid on this project's
  single persistent Node process on Hostinger, not serverless) rather than inventing a second
  mechanism.

### Confirmation page (`[locale]/{segment}/page.tsx`, exact segment TBD in planning)
- `metadata` export sets `robots: { index: false }` — no other metadata surface changes, no
  middleware edit (per 49-CONTEXT.md's explicit constraint).
- Keeps `SiteHeader`/`SiteFooter` (no bespoke headerless layout) — every other page on this site
  keeps the chrome, and there's no precedent or reason to strip it for a low-traffic utility page.
- Single-column, centered content inside the standard `Container`:
```
Container.py-16
  div.mx-auto.max-w-md.text-center

  [state: success — token valid, not expired]
    CheckCircle (lucide) .size-12.text-primary.mx-auto
    h1.font-heading.text-heading.mt-4   — "Confirmed!" / "¡Confirmado!"
    p.text-body.text-muted-foreground.mt-3  — success body
    Button asChild .mt-6.h-11
      a[href={signedCloudinaryUrl}]  — "Download the checklist (PDF)" / "Descargar el checklist (PDF)"

  [state: error — token invalid/expired/already-used]
    XCircle (lucide) .size-12.text-destructive.mx-auto
    h1.font-heading.text-heading.mt-4  — error heading
    p.text-body.text-muted-foreground.mt-3  — error body
    (no button — no destructive action, no retry action on THIS page; the retry path is going back
     to the article, which the body copy names explicitly instead of adding a second CTA button)
```
- **Manual download button, not an auto-redirect:** a `<meta httpEquiv="refresh">` auto-trigger was
  considered and rejected — Next.js App Router's `metadata` export has no first-class "refresh"
  field, and hand-rendering a `<meta>` tag from inside a page's JSX body does not reliably land in
  `<head>` (App Router pages render inside `<body>`). A plain server-rendered anchor styled as a
  primary button is simpler, fully zero-JS, and unambiguous — the user sees exactly what will
  happen and takes one deliberate click, which also reads better for a PDF (vs. a silent background
  download some browsers might block).
- The signed Cloudinary URL is generated server-side (by `secure-download.ts`, per MAIL-05) when this
  page renders the success state — never client-side, never embedded in the confirmation email
  itself (the email links to this confirmation page with the opt-in token; this page resolves the
  token to the signed download URL after verifying it, which is also what makes the "expired token"
  state possible to detect and render honestly).

### Zero client JS — confirmed feasible, no gotcha beyond what's noted above
This repo already proves the exact `<form action={serverAction}>` pattern ships zero incremental
client JS for a public form (`ContactFormBlockComponent`, Phase 5). This phase's only genuinely new
wrinkles are (1) mounting that pattern inside a Lexical rich-text converter tree for the first time
(previously only plain anchors lived that deep) and (2) threading `searchParams` into the
converters factory (both called out above) — neither requires client JS, both are pure Server
Component / Server Action wiring questions for the planner, not client-side interactivity gaps.

## PDF Layout (lead magnet — not a web page, no shadcn/Tailwind/webfont involvement)

Two locale-specific files (ES/EN), same layout, translated content. Generation mechanism (HTML→PDF
via headless Chromium, a PDF-generation library, etc.) is a research/planning decision — this
section specs the visual result, which holds regardless of mechanism.

**Page setup:** portrait, Letter or A4 (match whichever the mechanism defaults to — not worth
forcing a choice), 2.5cm margins on all sides (print-safe — avoids clipping on home/office printers,
since this is meant to be genuinely printable, not just screen-viewed).

**Fonts:** a system-safe sans stack (e.g. Helvetica/Arial, falling back per the mechanism's
defaults) for ALL text in the PDF — deliberately NOT `font-heading`/`font-display` (Khand/Array).
Webfont embedding in a build/seed-time PDF pipeline is an added dependency and failure surface for
a document whose whole design brief (per 49-CONTEXT.md) is "simple, honest, no elaborate design."

**Structure (single column, top to bottom):**
```
Header block
  H1 (bold, ~22-24pt) — "Technical SEO Audit Checklist" / "Checklist de auditoría SEO técnica"
  Byline (regular, ~11pt, muted gray) — "By Juan Carlos Angulo · juan-tech.com" / "Por Juan Carlos
    Angulo · juan-tech.com"
  Thin horizontal rule (accent color, #F7581E) — the ONE accent-color use in the entire document

5 category sections (repeated structure, in this fixed order):
  H2 (bold, ~14-16pt, black) — category name:
    1. Crawling & indexing / Rastreo e indexación
    2. Performance & Core Web Vitals / Rendimiento y Core Web Vitals
    3. Structured data / Datos estructurados
    4. Mobile & accessibility / Mobile y accesibilidad
    5. Security & canonicalization / Seguridad y canonicalización
  Unordered list, plain-text checkbox glyph per item (☐, not an interactive PDF form field — this
    is a printable/scannable checklist, always plain black text regardless of section):
    ☐ {actionable check, one short sentence + one clause on why it matters}
    (≥4 items per category, per the UI Considerations zero-one-many resolution above)

Footer (repeat on every page if the document runs multiple pages)
  Thin horizontal rule (neutral gray, not accent — accent is reserved for the one header rule)
  Small text (~9pt, muted gray) — "Juan Carlos Angulo · Software engineer & technical SEO
    consultant · juan-tech.com" / "Juan Carlos Angulo · Ingeniero de software y consultor SEO
    técnico · juan-tech.com"
```

**Color budget:** black text on white background for ~95% of the document (print-safe on any
