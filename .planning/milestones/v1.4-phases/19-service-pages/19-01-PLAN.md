<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL param → `payload.find({ where: { slug } })` | The `slug` route param on `/services/[slug]` and `/servicios/[slug]` (wired in 19-02) is attacker-controlled input that flows into a Local API query via `getServicePage` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-01 | Information Disclosure | `getServicePage(locale, slug)` in `src/lib/services-data.ts` | mitigate | `isServiceSlug()` allowlist check runs BEFORE any `payload.find` call — an arbitrary/attacker-supplied slug (e.g. a slug belonging to an unrelated unpublished `pages` doc) short-circuits to `undefined`/404 instead of ever reaching the database query, so this route can never be used to probe or leak content from other `pages` docs by slug-guessing |
| T-19-02 | Tampering | `src/lib/sitemap-data.ts` path branching | accept | Purely build-time/request-time URL string construction from already-trusted, already-public `SERVICE_SLUGS` constants — no user input reaches this code path, no new attack surface versus the pre-existing generic branch it extends |
| T-19-SC | Tampering | npm/pip/cargo installs | n/a | No new package installs in this plan — zero new supply-chain surface |

No new external input or write surface is introduced. `getServicesIndexPage`/`getServicePage`
reuse the `pages` collection's existing `authenticatedOrPublished` read access control unchanged.
</threat_model>
