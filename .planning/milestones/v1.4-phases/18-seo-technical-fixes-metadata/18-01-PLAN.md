## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-01 | Tampering | Authors `meta.title`/`meta.description` (new plugin-seo fields) | accept | Same access control as every other Payload collection field already in production (admin-authenticated write, public read via Local API `find`) — plugin-seo adds no new access-control surface, it reuses the Authors collection's existing `access: { read: () => true }` and default admin-only write; no new attack surface beyond what `pages`/`posts`/`case-studies` already expose via the same plugin |
| T-18-02 | Information Disclosure | Author page `<head>` meta title/description | accept | Both fields render only content the author/admin explicitly entered (or the pre-existing public `name`/`jobTitle` fallback) — no new PII exposed beyond what was already public in the rendered author profile |
| T-18-03 | Tampering | `<h1>` content sourced from `doc.meta?.title`/`doc.title`/`author.name` | accept | These are the same trusted Payload-admin-authored fields already rendered elsewhere on the same pages (page title, existing `<title>` tag, existing `<Link>` text) — no new user-controlled input path is introduced; React's default JSX escaping applies identically to the new `<h1>` as to the pre-existing markup |
| T-18-SC | Tampering | npm/pip/cargo installs | n/a | No new package installs in this phase — zero new supply-chain surface |

No new trust boundary crossings are introduced: this phase adds semantic markup around
already-trusted, already-rendered Payload content and extends an existing, already-vetted
plugin's collection list. No new external input, no new write surface beyond what Payload's
standard collection access control already governs.
</threat_model>
